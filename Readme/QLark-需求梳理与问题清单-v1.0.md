# QLark 1.0 需求梳理 · 矛盾点与缺口清单

> **文档版本**：v1.0
> **输入**：产品需求口述（QLark / 云雀 v1.0）
> **技术基線**：`Readme/QLark-NapCat部署技术文档.md` v1.1（实机验证结论，非文档转述）
> **本文用途**：把口述需求固化为可开发规格；标出**必须由你裁决**的地方。第 2 章的 15 条矛盾不裁决，写出来的代码大概率要返工。

---

## 0. 先给结论

需求方向是清晰的，产品定位（多人设 + 记忆 + 双击即用）也站得住。但当前描述存在：

| 类别 | 数量 | 严重度 |
|---|---|---|
| **硬矛盾**（同一句话里两个相反规则，或与已验证技术结论冲突） | 15 条 | 其中 5 条会导致"做完发现不能用" |
| **功能缺口**（完全没提，但不做就跑不起来 / 用不下去） | 约 60 项，归为 13 个模块 | 其中 11 项为 P0 |
| **GUI 技术选型**（你要求"不用老掉牙的库"，但 Python + 无黑窗 + 美观三者互相拉扯） | 1 项 | 决定整个前端架构，必须最先定 |

**5 个最危险的坑**（详见第 2 章）：

1. **记忆规则自相矛盾** —— "群聊共享一个记忆文件"和"不同人设有不同的记忆文件"是两个相反的要求，且完全没提"不同群之间"这个维度。按字面实现，A 群的聊天会串到 B 群。→ 这是数据表主键，后期返工要迁数据。
2. **压缩算法逻辑不闭合** —— "把摘要当作 20 轮的第 1 次回答"这个设计在角色语义上是错的，且轮数会漂移。
3. **人设作用域没定义** —— GUI 上 9 个标签是"编辑内容"还是"激活生效"？一个群的 `/person 3` 会不会把其他群的人设也改掉？
4. **扫码成功 ≠ 机器人可用** —— 按你的描述，登录完就结束了；但实测结论是：**登录后还必须写 OneBot 网络配置并重启 NapCat**，否则一个消息都收不到（协议端默认不开任何端口）。
5. **首次运行环境自检完全没提** —— VC++ 运行库 + `crypto.dll` + `ssl.dll` 三件套缺一不可，而官方 Node 包**本身就缺后两个 DLL**（上游打包缺陷）。不做这步，"双击即开"直接不成立。

## 1. 需求梳理（结构化重述）

### 1.1 产品定位与硬约束

| 项 | 需求原文 | 技术可实现性 | 备注 |
|---|---|---|---|
| 形态 | Windows 桌面客户端，双击图标即用 | ✅ 可行 | 依赖技术文档已验证的 `-q` 快速登录免扫码 |
| 无黑窗 | "无多余黑窗口" | ✅ 可行 | `subprocess.Popen(..., creationflags=CREATE_NO_WINDOW)` |
| 窗口内看日志 | 日志页展示 NapCat 运行日志 | ⚠️ 需配套设计 | 必须**持续读 stdout**，否则管道缓冲写满会**卡死 NapCat**（技术文档坑 23） |
| 魔法值 | 无 Python/Node/命令行前置 | ⚠️ 有前提 | 需内置 VC++ 静默安装 + 两个 DLL + 约 300MB NapCat 运行时 |
| 语言 | Python | ✅ | 仓库 `.venv` 为 Python **3.13.13**（注意 `.idea` 里写的是 3.13，本机 PATH 上是 3.11，需统一） |
| 协议 | 基于 NapCat，OneBot 11 | ✅ | 已实测：`127.0.0.1:3000` HTTP 服务端 + Bearer token |

### 1.2 技术链路（按已验证结论固化）

```
QQ 消息
  → NapCat（node.exe ./index.js -q <QQ号>，静默 spawn，工作目录 runtime/napcat）
  → OneBot 11 HTTP 服务端  127.0.0.1:3000  Authorization: Bearer <token>
  → QLark 业务层
      ├─ 触发判定（群聊必须 @）
      ├─ 指令解析（/person N）
      ├─ 记忆装配（人设 + 摘要 + 近 N 轮）
      ├─ 图像处理（下载 → 压缩 → base64）
      ├─ OpenAI 兼容 API 调用
      └─ 回复（send_msg）+ 落库 + 统计
```

**已验证的关键事实（不要重新验证，直接用）**：

- 改 `config/*.json` **不支持热重载**，必须重启 NapCat
- WebUI 内部 API 是 HMAC 动态密钥，**静态 token 调不通** → 直接读写配置文件，不要走 WebUI
- 杀进程必须杀**父进程树**（`taskkill /PID <父PID> /T /F`），只杀 worker 会被自愈机制重拉
- `cache/qrcode.png` **登录成功后不删除**，且**每约 121 秒覆盖重写**
- 图片 URL **约 2 小时过期**，必须立即下载
- NapCat 无数据库，消息 LRU 约 5000 条过期，消息 ID 非连续

### 1.3 页面清单与需求元素

| 页面 | 需求元素 | 我的补充标记 |
|---|---|---|
| 全局 | 黑夜/白天主题，默认黑夜；不用老 GUI 库；字体优先微软雅黑 | 主题需持久化；二维码不能反色（见 3.10） |
| 全局右上角 | 登录按钮常驻、不随模块切换消失；点击显示扫码登录 | 已登录时应显示账号态而非二维码（见 2.1-⑦） |
| 仪表盘 | 今日 Token 消耗、今日调用次数、连接状态、当前 QQ 号 | 缺 8 项，见 3.8 |
| 模型配置 | 最大输出 Token、温度等；OpenAI 格式 API；应用按钮（免重启）、测试按钮（省 Token） | 测试策略需修正（见 2.1-⑧）；需多模型槽位（见 3.4） |
| 人设配置 | 人设 1~9 共 9 个标签；默认人设 1（系统级）；`/person N` 切换；未设置也能切（空人设） | 作用域与权限未定义（见 2.1-⑤⑥） |
| 记忆面板 | 群聊共享记忆、人设间隔离；私聊按用户隔离；记忆轮数（默认 20）；总结轮数（默认开启） | 规则自相矛盾（见 2.1-①②③④） |
| 日志输出 | 放 NapCat 运行日志 | 需区分 QLark 自身日志与 NapCat 原始输出（见 3.9） |

### 1.4 消息触发规则

| 场景 | 规则 | 需澄清 |
|---|---|---|
| 群聊 | 必须 @机器人 才触发 | @全体成员是否算？@昵称文字是否算？被 @后是否需要引用回复？ |
| 私聊 | 无限制 | 是否响应陌生人/临时会话？ |
| 指令 | 群聊 `@机器人 /person 1`；私聊直接 `/person 1` | 全角 `／` 是否兼容？非法参数如何反馈？ |

### 1.5 人设模型（当前描述的隐含结构）

```
人设 1 ── 系统提示词（"系统级"，含义待澄清）
人设 2 ── 系统提示词
 ...
人设 9 ── 系统提示词
默认激活：人设 1
空人设  ：未配置时不注入 system，等同裸模型输出
```

### 1.6 记忆模型（当前描述的隐含结构）

```
群聊：所有成员共享 ─┬─ 人设 1 → 记忆文件 A
                   ├─ 人设 2 → 记忆文件 B
                   └─ ...
私聊：按用户隔离   ─┬─ 用户甲 × 人设 1 → 记忆文件 X
                   ├─ 用户甲 × 人设 2 → 记忆文件 Y
                   └─ 用户乙 × 人设 1 → 记忆文件 Z

压缩：满 20 轮 → AI 压缩到 ≤300 字 → 删除这 20 轮 → 摘要成为"第 1 轮的回答" → 循环
```

### 1.7 模型调用

- 仅支持 **OpenAI API 格式**（`/chat/completions`）
- 支持 **图片理解**（base64 内联，`image_url` 段）
- 配置项：API Key、Base URL、模型名、最大输出 Token、温度
- 热生效：应用后不重启

### 1.8 非功能需求

| 项 | 需求 | 状态 |
|---|---|---|
| 美观 | 整洁美观、主题切换 | 需定框架 |
| 无黑窗 | 必须 | 需配套 stdout 消费线程 |
| 易用 | 双击即开 | 需首启向导 + 环境自检 |
| 稳定 | —— | **未提，是最大空白**（单实例、孤儿进程、崩溃恢复） |
| 安全 | —— | **未提**（API Key 存储、群聊内容外发提示） |
| 合规 | —— | **未提**（QQ 风控/封号风险告知） |

## 2. 矛盾点清单（15 条）

### 2.1 A 类：需求内部自相矛盾（必须二选一）

---

**① 群聊记忆到底"共享"还是"隔离"？——同一句话里两个相反规则**

> 原文："本软件群聊中共享一个记忆文件，但是不同人设有不同的记忆文件，互相影响"

三重问题：

1. "共享一个记忆文件" 与 "不同人设有不同的记忆文件" 直接互斥；
2. "**互相影响**" 与前半句的隔离意图相反，几乎确定是"**互不影响**"的笔误——但按字面读则是"记忆互相污染"，意思完全反过来；
3. **完全没提"不同群之间"这个维度**。按字面理解（人设 1 只有一份记忆文件），**A 群的对话会串进 B 群**，机器人在 A 群说的话会被它当成在 B 群说过。

**影响**：这是记忆表主键 + 文件路径规则，属于数据模型地基。定错后期要迁移全部历史记忆。

**建议裁决**：会话键 = `(会话类型, 会话ID, 人设ID)`

| 场景 | 键 | 效果 |
|---|---|---|
| 群聊 | `group:<群号>:p<人设ID>` | 同群全成员共享一份；同群不同人设各自一份；**不同群互不干扰** |
| 私聊 | `private:<QQ号>:p<人设ID>` | 每个用户独立；同用户不同人设各自一份 |

> 若你**确实**想要"A 群和 B 群共享同一人设的记忆"（跨群人格连续性），请明确说明——这是另一种产品设计，也成立，但必须写清楚。

---

**② "记忆轮数" 和 "总结轮数" 的关系完全没定义**

> 原文："记忆轮数设置框（默认记忆20轮对话,可修改）" / "总结轮数设置框（默认开启）"

两个参数各自是干什么的、怎么联动，都没说。可能的三种语义，实现完全不同：

| 语义 | 记忆轮数 | 总结轮数 | 行为 |
|---|---|---|---|
| 解释 A | 上下文窗口（发给 AI 的轮数） | 压缩触发阈值 | 两者独立，用户可设 记忆=20 / 总结=10 |
| 解释 B | 落库保留轮数 | 同左，冗余参数 | 两个框重复，应删一个 |
| 解释 C | 压缩后保留的轮数 | 压缩前的累积轮数 | 逻辑绕，易出 bug |

**若按解释 A 且用户设成 记忆=30、总结=20**：什么时候压缩？压缩后窗口里剩几条？需求没有答案。

**建议裁决**：采用**解释 A**，并明确规则：
- **记忆轮数 W** = 每次请求携带的最近原文轮数（默认 20）
- **总结触发轮数 S** = 未压缩原文累积到 S 轮时触发压缩（默认 = W）
- **摘要不计入 W**，它是独立"记忆块"（见 ③）

---

**③ "把摘要当作 20 轮的第 1 次回答" —— 角色语义错误 + 轮数漂移**

> 原文："删除20对话历史，将总结出的内容，作为20轮对话的第1轮出现。也就是说会把总结出的记忆聊天记录，当作20轮的第一次回答。"

三个问题：

1. **一轮 = 一问一答**。若摘要是"第 1 次回答"，那对应的"第 1 个问题"是什么？缺口无法填。
2. **角色错乱**：摘要是 AI 对整段对话的**第三方概述**（"用户问了 X，我回答了 Y"），把它塞进 `assistant` 角色，等于让模型认为**这段概述是自己亲口说过的话**。模型会倾向于模仿这种"元叙述"口吻，人格漂移、说话变得像会议纪要。
3. **轮数漂移**：摘要占了 1 轮的位置，那么本次应该只删 19 轮原文还是 20 轮？下次触发点是"再满 20 轮"（累计 21 个单位）还是"补满窗口"（累计 19 轮）？没有定义，实现者只能猜。

**建议裁决**：摘要作为**独立记忆块**注入，不占轮次、不是对话消息，放在 system 区（或紧邻 system 的第一条），格式：

```
[长期记忆摘要] 用户与机器人此前讨论了 ……（≤300 字）
```

并规定：**只有原文轮数计入 W 和 S**；摘要可以无限次递归合并（旧摘要 + 新 20 轮 → 新摘要），但要接受信息随时间衰减，这是压缩的固有代价。

---

**④ "总结轮数设置框" 到底是数字还是开关？**

> 原文："总结轮数设置框（默认开启）"

"轮数设置框"暗示它填数字，"默认开启"暗示它是开关。二者不能是同一个控件。

**建议裁决**：拆成两个控件 —— `☑ 启用自动总结` + `触发轮数 [20]`。且开启开关默认勾选，轮数输入框在未勾选时置灰。

---

**⑤ 人设的"生效作用域"未定义 —— GUI 单槽位 vs 会话多实例**

- GUI 描述："有 9 个选项，**点击对应的标签即可更改对应的人设**，默认使用的人设 1"
- 群聊描述："用户在群聊里 @机器人 `/person 1` 即可成功切换人设 1"

这两条隐含两种不兼容的模型：

| 模型 | 含义 | 后果 |
|---|---|---|
| **全局单槽位** | 整个软件同时只有一个"当前人设" | 甲群有人发 `/person 3`，**乙群、所有私聊的人设全部被改掉**，且他们各自的记忆文件也随之切换 —— 实际是灾难 |
| **会话独立** | 每个群 / 每个私聊各自记住自己的当前人设 | 符合直觉，但"点击 GUI 标签"改的是谁？ |

**建议裁决**：**会话独立**，并把 GUI 语义拆清楚：
- GUI 的 9 个标签 = **人设内容编辑器**（改名字、头像、提示词）
- GUI 上另设一个"设为新会话默认人设"操作 = 修改**默认人设**（默认人设 1）
- 每个群 / 每个私聊各自维护"当前人设"，初始值 = 默认人设

---

**⑥ `/person` 的权限：任何群成员 vs 仅管理员**

需求说"管理员没有在 GUI 页面里设置"——暗示人设由管理员管理；但又说"用户在群聊里 @机器人 `/person 1` 即可成功切换"，没有任何权限限制。于是：**群里任何人一句 `/person 9` 就能把整个群的机器人记忆和人设换掉**。这是权限漏洞，也是产品风险（恶作剧）。

**建议裁决**：加一个权限开关，默认取安全值：
- 群聊：**默认仅管理员**（管理员 QQ 白名单，在 GUI 里配置）；可放开为"所有成员"
- 私聊：本人可切（默认允许）

---

**⑦ 登录按钮"点击即显示扫码" —— 已登录时是错的**

> 原文："点击这个登录按钮之后会显示扫码登录"

两个问题：

1. **已登录时**（这正是常态，因为 `-q` 快速登录免扫码）：点登录按钮却弹出二维码，用户会以为掉线了。正确行为是显示 **账号态面板**：`已登录 2157649443（米蛋）` + `在线/离线` + `退出登录` + `切换账号`，二维码只在需要时（凭据失效 / 切换账号 / 首次使用）出现。
2. **与技术文档最核心的结论冲突**：`-q <QQ号>` 免扫码快速登录是"双击即开"唯一成立的方式（技术文档 §8.2、§9.2）。"点击登录 → 扫码"是这个流程的**兜底分支**，不是主流程。

**建议裁决**：登录按钮 → 打开**登录面板（模态）**，内部是一个状态机：优先快速登录 → 失败才降级扫码（见 4.4）。

---

**⑧ 测试按钮："发送测试信息" vs "不要花多余的 Token"**

> 原文："测试按钮会发送一段测试信息……（这里发送的测试信息仅仅只是测有没有连通，不要花多余的Token）"

严格说，任何 `/chat/completions` 请求都会产生**输入 token 成本**（最低约 5~10 token），"不花多余 token"只能做到"几乎不花"，做不到"不花"。而且"发一条测试信息"测的是**对话能力**，不是**连通性**——两者不等价。

**建议裁决**：分层测试，默认零 Token：

| 层级 | 手段 | Token | 能验证什么 |
|---|---|---|---|
| L1（默认） | `GET {base_url}/models` | **0** | 网络连通、鉴权、**配置的模型名是否存在** |
| L2（L1 不支持时自动降级） | `POST /chat/completions`，`max_tokens=1`，prompt 用 `"1"` | ~6 | 对话接口是否真的可用 |
| L3（可选勾选"深度测试"） | 带一张小图的最小视觉请求 | ~100+ | 视觉能力是否可用（**这个必须显式勾选**，因为很多模型不支持视觉） |

并且错误要分类回显，而不是笼统"异常"：`401 鉴权失败` / `404 地址或模型名不存在` / `429 限流` / `连接超时` / `TLS 证书错误`。

---

**⑨ "连接状态（是否在线）" —— 指哪个在线？**

需求把"连接状态"和"目前登录QQ号"并列放在仪表盘。但系统里有**两条独立的连接**：

| 连接 | 断了会怎样 | 判据 |
|---|---|---|
| **QQ / NapCat 链路** | 收不到消息、发不出去 | `get_status` → `{"online": true}`；3000 端口监听 |
| **模型 API 链路** | 收到消息但回不了话 | 最近一次调用结果 / 定期探活 |

**建议裁决**：仪表盘放**两个独立状态灯**，别合成一个"在线"。

---

### 2.2 B 类：与已验证技术结论冲突（按技术结论改）

---

**⑩ 扫码登录成功 ≠ 机器人可用（最危险的缺口）**

按需求描述，用户扫码 → 登录完成 → 结束。但实测结论是：

```
NapCat 新装后，四种网络模型全是空数组 —— 一个端口都不监听。
必须写 onebot11_<QQ号>.json 并【重启 NapCat】才生效。
```

所以真实流程必须在"登录成功"后面接两步：

```
登录成功 → 检查 onebot11_<QQ号>.json 的 network 段
         ├─ 未配置 → 按模板合并写入（先备份）→ 重启 NapCat
         └─ 已配置 → 直接用
         → 轮询 3000 端口就绪 → 才算"可用"
```

**只做需求描述里的流程，结果是"登录成功了但机器人一句话都不回"**，且新手完全无法自查。

---

**⑪ "应用后无需重启" 的适用范围被放大了**

需求说模型配置"点击应用后无需重启软件即可成功应用"——这对**模型/人设/记忆参数**成立（QLark 自己的内存态）。但同一句话很容易被推广成"所有配置都免重启"，那就错了：**任何 NapCat 侧的配置（OneBot 端口、token、日志开关）都必须重启 NapCat 才生效**。

**建议**：GUI 里对需要重启的项明确标注 `⚠ 需重启 NapCat`，并提供"立即重启"按钮。

---

**⑫ 首次运行环境自检 —— 需求零提及**

技术文档 §9.4 明确规定首启必须自检三样，缺一不可：

| 检查项 | 缺失后果 | 补齐方式 |
|---|---|---|
| VC++ 运行库（`vcruntime140.dll` 等） | `wrapper.node` 加载失败，程序直接起不来 | 内置 `vc_redist.x64.exe` 静默安装 |
| `crypto.dll`（~1.5MB） | 同上 | **必须随包内置**（官方 Node 包根本没这个文件） |
| `ssl.dll`（~0.5MB） | 同上 | 同上 |

"从官方 QQ 里拷两个 DLL"这条路**不能给终端用户用**（要装 QQ、要 winget、要翻注册表），必须内置。同时要预期：**杀软可能误报内置 DLL**，需在首启和文档里说明。

---

**⑬ 二维码残留与自动刷新（做出来就是 bug）**

| 坑 | 现象 | 必须做的事 |
|---|---|---|
| 坑 21 | `cache/qrcode.png` 登录成功后**不删除**，界面显示上次的过期码 | **启动 NapCat 前先删除该文件**；判据 = 文件出现 **且** mtime > 进程启动时间 |
| 坑 22 | 二维码**每约 121 秒覆盖重写**同名文件 | 监听 mtime 变化并刷新，**不能静态展示** |

需求只写了"显示扫码登录"，按最直白实现必然踩这两个坑。

---

**⑭ "无黑窗" + "日志页" 必须配套设计，否则会卡死 NapCat**

实测坑 23：NapCat 启动输出（含大幅二维码字符画）**如果没被持续读取**，管道缓冲区写满后**进程阻塞**。

"无黑窗"（`CREATE_NO_WINDOW`）+ "GUI 显示日志"（必须拿到 stdout）这两个需求合起来，强制要求：**独立读线程持续消费 stdout，写入环形缓冲 + 日志文件**。任何"开了进程但偶尔才读一次"的写法都会随机卡死。

---

**⑮ 图片 URL 2 小时过期 —— 不能直接转发 URL**

需求给的示例是本地读文件转 base64，但 QQ 消息里的图片 NapCat 给的是 **URL**，而且**约 2 小时后失效**。

**必须做**：收到图片消息 → **立即下载**（超时保护 + 大小上限）→ 落临时文件或内存 → 转 base64 → 发给模型。任何"先把消息存进记忆，稍后再处理图片"的设计都会在 2 小时后拿到 `url expired`。

## 4. 建议的规格补全（可直接采用）

### 4.1 记忆数据模型（建议定稿）

**会话键**：

```
群聊： group:<群号>:p<人设ID>      例  group:123456:p1
私聊： private:<QQ号>:p<人设ID>    例  private:2157649443:p3
```

**存储**：SQLite（WAL），单文件 `%LOCALAPPDATA%\QLark\data\qlark.db`

```sql
-- 对话原文（只存触发了机器人的问答）
CREATE TABLE messages (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  session_key TEXT    NOT NULL,
  role        TEXT    NOT NULL,   -- user | assistant
  content     TEXT    NOT NULL,
  has_image   INTEGER DEFAULT 0,
  tokens      INTEGER DEFAULT 0,
  msg_id      TEXT,               -- 用于去重，NapCat 消息 ID
  created_at  INTEGER NOT NULL,
  summarized  INTEGER DEFAULT 0   -- 是否已被压缩
);
CREATE INDEX idx_msg_session ON messages(session_key, summarized, id);

-- 每个会话当前生效的摘要（一个会话最多一条）
CREATE TABLE summaries (
  session_key TEXT PRIMARY KEY,
  content     TEXT NOT NULL,
  covered_to  INTEGER NOT NULL,   -- 已覆盖到哪条 message id
  updated_at  INTEGER NOT NULL
);

-- 每人设 × 每会话的当前激活人设
CREATE TABLE session_state (
  session_key  TEXT PRIMARY KEY,
  active_persona INTEGER NOT NULL DEFAULT 1,
  updated_at   INTEGER NOT NULL
);

-- 每日统计（跨天重置靠 date 字段）
CREATE TABLE stats_daily (
  date        TEXT NOT NULL,
  session_key TEXT NOT NULL DEFAULT '*',
  prompt_tokens     INTEGER DEFAULT 0,
  completion_tokens INTEGER DEFAULT 0,
  calls       INTEGER DEFAULT 0,
  errors      INTEGER DEFAULT 0,
  msg_in      INTEGER DEFAULT 0,
  msg_out     INTEGER DEFAULT 0,
  PRIMARY KEY (date, session_key)
);

-- 人设
CREATE TABLE personas (
  id           INTEGER PRIMARY KEY,   -- 1..9
  name         TEXT    DEFAULT '',
  avatar_path  TEXT    DEFAULT '',
  system_prompt TEXT   DEFAULT '',
  enabled      INTEGER DEFAULT 0,
  model_override TEXT  DEFAULT NULL,
  temperature_override REAL DEFAULT NULL,
  max_tokens_override  INTEGER DEFAULT NULL
);
```

> 注：需求说的是"记忆文件"。若坚持文件形态，也必须做到**原子写**（写临时文件 + `os.replace`）并加进程锁；否则并发写会损坏。但我建议 SQLite —— 它是文件，且天然解决并发与断电。

### 4.2 记忆压缩算法（修正版）

```
参数
  W = 记忆轮数（默认 20）        送给模型的最近原文轮数
  S = 总结触发轮数（默认 = W）    未压缩原文累积到多少轮触发压缩
  K = 摘要字数上限（默认 300）

每完成一次成功的问答（写入 user + assistant 两条）后：
    rounds = count(该 session 中 summarized = 0 的完整轮数)

    if rounds >= S:
        material = [当前摘要(若有)] + [最早的 S 轮原文]
        new_summary = LLM(总结模型, material, "压缩到 300 字以内，保留事实与用户偏好")
        if new_summary 失败:
            标记 pending，本轮不压缩，【不删除任何原文】   ← 关键保护
            return
        事务 {
            写入 / 更新 summaries
            把这 S 轮原文标记 summarized = 1（或删除）
        }

组装请求时的上下文：
    messages = [
        {"role": "system",    "content": 人设提示词（为空则整个不发）},
        {"role": "system",    "content": "[长期记忆]\n" + 摘要},   ← 若服务商只接受单条 system，则并入上一条
        ...最近 W 轮原文...
        {"role": "user",      "content": 本轮消息（含图片段）}
    ]
    若 token 估算 > 预算：从最早的原文开始丢弃，摘要始终保留
```

**与需求原文的差异**：摘要**不占轮次、不是 assistant 消息**；触发依据是"未压缩轮数"而非"窗口是否满"，因此 W 与 S 解耦，用户可以自由改。

### 4.3 人设作用域与权限（建议）

| 概念 | 存放位置 | 谁能改 |
|---|---|---|
| 人设内容（1~9） | `personas` 表 | GUI 管理员 |
| 默认人设 | 全局配置 | GUI 管理员（"设为新会话默认"） |
| 会话当前人设 | `session_state` 表 | `/person N` 指令，受权限开关控制 |

- 群聊 `/person` 默认**仅管理员**（管理员 QQ 白名单在 GUI 配置），可放开为所有成员
- 私聊 `/person` 默认允许本人
- 切换后回一条确认："已切换为人设 3：傲娇女仆"
- 切换指令**不写入记忆**

### 4.4 登录与启动状态机（建议）

```
[启动]
  ├─ 单实例锁（已有实例 → 激活已有窗口，退出）
  ├─ 环境自检：VC++ / crypto.dll / ssl.dll / 端口可用性
  │     └─ 缺失 → 自动补齐（VC++ 静默装；DLL 从内置副本拷）
  ├─ 清理孤儿 node.exe（上次崩溃残留）
  ├─ 读取本地保存的 QQ 号
  │     ├─ 有 → 删 cache/qrcode.png → spawn: node.exe ./index.js -q <QQ号>
  │     │        ├─ 日志出现「正在快速登录」+「Worker进程已登录成功」→ 登录成功
  │     │        └─ 日志出现「将使用二维码登录方式」→ 降级到扫码分支
  │     └─ 无 → 扫码分支
  ├─ 扫码分支
  │     ├─ spawn: node.exe ./index.js（不带 -q）
  │     ├─ 轮询 qrcode.png：出现且 mtime > 进程启动时间 → 显示
  │     │                     mtime 变化（约 121s）→ 刷新显示
  │     └─ 登录成功 → 隐藏二维码 → 保存 QQ 号到本地配置
  ├─ 初始化网络
  │     └─ 检查 onebot11_<QQ号>.json 的 network 段
  │           ├─ 已启用 → 跳过
  │           └─ 未配置 → 备份 + JSON 合并写入 → 重启 NapCat（杀父进程树）
  ├─ 轮询 127.0.0.1:3000 就绪 → get_status 验证 → 仪表盘绿灯
  └─ [就绪] 开始消费消息
```

### 4.5 消息处理流水线（建议）

```
事件到达
  → 去重（msg_id）
  → 过滤（自己 / 其他机器人 / 系统消息 / 黑名单）
  → 触发判定（群聊：at 段含机器人 user_id；私聊：全部）
  → 指令分支（/person、/reset、/help）—— 不进记忆
  → 入队（按 session_key 串行；全局并发上限 N）
  → 图片处理（立即下载 → 缩放 → base64）
  → 装配上下文（人设 + 摘要 + 最近 W 轮 + 本轮）
  → 调用模型（超时 / 重试 / 失败提示）
  → 回复（分段 / 引用）
  → 落库（原文 + 统计）
  → 检查是否触发压缩
```

## 5. GUI 框架选型（对应"不要用老掉牙的 GUI 库"）

这是**第一个必须做的技术决策**，因为它同时决定：界面美观上限、打包体积、二维码渲染、日志性能、开发速度。

| 方案 | 美观上限 | 打包体积 | 无黑窗 | 学习成本 | 评价 |
|---|---|---|---|---|---|
| **pywebview + HTML/CSS/JS**（WebView2） | ★★★★★ | ~150MB + 运行时 | ✅ | 中（要写前端） | **最推荐**：Web 技术做深色主题/圆角/动效最省力；二维码直接 `<img>`；日志用虚拟滚动 |
| **PySide6 + QSS** | ★★★★ | ~150MB | ✅ | 中 | 推荐备选：纯 Python 单技术栈，`QWebEngineView` 也能塞 HTML；LGPL 需注意合规 |
| **Flet**（Flutter 内核） | ★★★★ | ~120MB | ✅ | 低 | 好看且写起来快，但生态较小、自定义受限于其组件 |
| CustomTkinter | ★★★ | ~40MB | ✅ | 低 | 比 Tkinter 好看一个档次，但仍能看出"Tkinter 味"，做不出你要的"不凌乱" |
| Tkinter | ★ | ~30MB | ✅ | 低 | **明确排除** —— 就是你说的"老掉牙的库" |
| Electron / Tauri | ★★★★★ | 100MB+ | ✅ | 高 | 与"编程语言：Python"冲突，且要维护两套技术栈 |

**我的建议**：`pywebview`（后端 Python + 前端 HTML/CSS/JS）。

理由：
1. 深色/浅色主题、字体（微软雅黑）、圆角、卡片布局用 CSS 是**最低成本**的实现方式；
2. 二维码就是一张 PNG，`<img src>` 直接显示，刷新只改 `?t=<mtime>` 破缓存；
3. 日志页用虚拟滚动列表，几千行也不卡；
4. Python 侧继续用 `subprocess` + 线程读 NapCat stdout，与前端用 `pywebview` 的 JS API 桥接。

**代价（必须提前接受）**：
- 依赖 **Edge WebView2 Runtime** —— Win11 与大多数 Win10 已内置，但必须在首启自检里检测，缺失时引导安装；
- 打包体积约 150MB（pywebview 会带上 Python + 运行时）；
- 需要写前端代码（深色主题的 CSS 变量，工作量不大）。

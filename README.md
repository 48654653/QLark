# QLark 云雀

基于 [NapCat](https://github.com/NapNeko/NapCatQQ) 的 QQ 聊天机器人 **Windows 桌面客户端**：
双击打开、扫码登录、在图形界面里配置，不用改配置文件也不用碰命令行。

适配任何 **OpenAI API 兼容**的服务（DeepSeek / MiMo / OpenAI / 自建中转都行），
主打 **多人设对话** 与 **长期记忆**，群聊和私聊都能用。

- 版本：**v2.2** ｜ Python 3.13 ｜ 界面 pywebview（Edge WebView2）｜ 协议 OneBot 11

> [!WARNING]
> **仅供学习交流。** 请遵守腾讯 QQ 用户协议与当地法律法规。
> 使用非官方客户端存在被风控甚至封号的风险，**请自行评估、自担后果**。

## 特性

| | |
|---|---|
| **多人设** | 一份人设一套性格、口癖、提示词；不同群挂不同人设，记忆互不串味 |
| **长期记忆** | 按 `<会话>:<人设>` 独立存储，满轮自动压缩成摘要，上下文不会无限膨胀 |
| **模型自主决定回复形态** | 回多长、分不分段、配不配表情、发不发语音，全都由模型看情境判断，**没有骰子** |
| **免 @ 接话** | @ 一次之后一段时间内不用再 @，而且不会因为对方连发碎片就回一串「嗯」 |
| **能听能说** | 引用消息里的文字、图片、视频、聊天记录都读得到；短句可以发成语音 |
| **看图** | 收到图片先交给视觉模型理解，而且**最近几轮的图片会留在上下文里** |
| **风控** | 限流、敏感词、白名单、@ 触发，尽量别把号玩坏 |
| **全图形界面** | 登录、配置、人设、记忆、日志都在一个窗口里，暗色 / 亮色主题 |

## 核心设计：为什么没有骰子

v1 用随机数决定「这一轮要不要分段」「要不要配表情」「回多长」。
这个做法有个根本问题：**上下文盲** —— 在生成之前就把形态定死了，根本不知道对方正在说什么。

v2 把这套骰子**全部删掉**，改成让模型自己判断：

| 以前（代码掷骰子） | 现在（模型判断） |
|---|---|
| 25% 概率分段 | 想分几条就分几条（有上限） |
| 20% 概率配表情 | 这句好笑就配，不好笑就不配 |
| 25%/35%/10% 长度档位 | 打招呼就两个词，对方在情绪里就认真回 |
| — | 短句可以发成语音 |

代价是失去了固定频率控制，所以提示词里给的是**判断标准**而不是概率，
并且在仪表盘的「回复形态」卡片里显示实际使用率 —— 太高就回去调提示词。

**每一轮**都会注入【输出规则】和末尾的格式提醒，模型只输出一个 JSON 对象：

```json
{"messages": ["第一句", "第二句"], "meme": "开心", "voice": false, "emotion": "开心"}
```

代码只负责**护栏**，不负责删内容：
语音超过字数就改发文字、分段超过上限就合并、表情名不在目录里就忽略、
JSON 解析失败就先让模型重写一次，还不行就把原文抢救出来照发 —— **绝不因为格式问题把回复丢掉**。

## 免 @ 接话：保活 + 合并

群里每说一句都得 @ 一次非常烦人，但"不 @ 也永远回"会让机器人变成每句都插嘴的复读机。
所以做了两层：

### ① @ 激活保活

```
A @ 机器人        → 开一个 60 秒的窗口，回他
A 继续说（不 @）   → 窗口续期，照常回
A 停满 60 秒      → 窗口自动关闭，之后又要 @ 才会理
```

**窗口按 `(会话, 用户)` 独立。** 别人说话既不能给他续期、也不能蹭用他的窗口 ——
否则群里一直有人说话窗口就永远不关，那比"每句都要 @"更糟。

### ② 连发消息合并

有人习惯把一句话拆成好几条发（"在" "吗" "问个事"）。每条都回会变成
「咋了 / 嗯？ / 说」三连。所以窗口内的消息先攒起来：

```
对方：在            ┐
对方：问个事        │  全部进缓冲，计时重置
对方：你有空吗      ┘
── 静默 3 秒 ──
机器人：一次回完这三条
```

- **静默 3 秒**后合并发出；每来一条碎片就重新计时
- **硬上限 15 秒**：从第一条算起，防止对方一直打字导致永远不吭声
- **@ 立刻回**，但会把已攒的碎片一起吸收进来，不会先回一个「嗯？」再回正式答案
- 合并后每个碎片**一行**进记忆，保留"他是一句一句发的"这个信息

> 为什么不用"每 15 秒轮询一次"：那样单条消息的延迟取决于它恰好落在哪个格子里
> （0～15 秒随机），同样的话忽快忽慢，比稳定偏慢更假。

## 语音回复

调用 MiMo 的 `mimo-v2.5-tts-voicedesign`（自定义音色），**共用对话的 Base URL 和 Key**，
只单独配模型名。模型在 JSON 里写 `"voice": true` 时才会走语音。

几条实测得到的约束，都已经写进代码里了：

- **不需要自己转 silk** —— NapCat 发送时会检测并自动调用转换（日志会打「语音文件X需要转换成silk」）
- **必须 ≤ 20 字**：46 个字要念 21 秒，没人愿意听完长语音
- **只能发一条**：多条语音会变成连续轰炸
- **任何一环失败都退回文字**：合成报错、超时、返回空音频、写文件失败，一律改发文字，绝不丢回复

音色描述写在「人设配置 → 音色描述」里。它是决定声音年龄感的关键：

| 写法 | 效果 |
|---|---|
| 小女孩、奶气、轻快 | 稚嫩（约 286 Hz） |
| 少女、清透干净 | 清纯 |
| 慢半拍、慵懒、有笑意 | **会变成成熟御姐**，慎用 |

## 引用消息

别人引用一条消息再说话时，机器人会去把被引用的内容取回来看：

| 类型 | 处理 |
|---|---|
| 文字 | 直接拼进上下文 |
| 图片 | 交给多模态（最多 2 张） |
| 视频 / 语音 / 表情 / 文件 | 渲染成标记，至少知道"那里有个视频" |
| 转发的聊天记录 | 展开成「甲：… / 乙：…」 |

OneBot 的 `reply` 段只带消息 ID 不带内容，所以要额外调一次 `get_msg`。
**取不到就当作没有引用**，绝不卡住回复（对方可能已经把原消息删了）。

## 记忆

- 按 `<会话>:<人设>` 独立存储，群聊里所有人**共用一份**记忆
- 满 N 轮自动压缩成摘要，摘要永远保留，超预算时先丢最早的原文
- **图片不存 base64**，只存文件名，图片本体在 `<数据目录>/media/`
- **最近 2 轮的真实图片会放回上下文**，更早的退化成纯文本
- 机器人自己说的话存**模型原始输出的 JSON** —— 这样回看历史时示范也是 JSON，格式自洽

## 快速开始

### 1. 准备 NapCat 运行时

QLark 本身**不带** NapCat。两种方式：

- **用带运行时的发布包**（推荐，开箱即用）
- **自己放**：把 NapCat 目录放到 QLark 的 `runtime/napcat/` 下，或在配置里指定路径

首次启动如果没找到，界面会提示，跟着向导走即可。

### 2. 安装依赖

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

### 3. 配置模型

双击打开 QLark → 首启向导，或者进「模型配置」页：

| 字段 | 填什么 |
|---|---|
| Base URL | `https://api.deepseek.com/v1` 或你的服务地址 |
| API Key | 对应服务的 Key |
| 模型名 | 例如 `deepseek-chat`、`mimo-v2.6-flash` |
| 视觉模型 | 可选，要让它看图就填 |
| 语音合成模型 | 可选，例如 `mimo-v2.5-tts-voicedesign` |

点「应用」即可，不用重启。

### 4. 运行

```powershell
python run.py
```

或者双击打包好的 `QLark.exe`。

## 配置项说明

「模型配置 → 对话行为」里按功能分成了六组：

### 对话节奏
| 项 | 默认 | 说明 |
|---|---|---|
| 记忆轮数 | 20 | 上下文里带多少轮原文 |
| 单条回复最大字数 | 500 | 超出截断，避免刷屏 |
| 每分钟回复上限 | 0 | 单会话每分钟最多几条，0 = 不限制 |
| 多条之间的间隔（毫秒） | 500 | 分段发送之间的停顿 |

### 回复形态
| 项 | 默认 | 说明 |
|---|---|---|
| 回复判断表 | 开 | 教模型按情境判断该回多长 |
| 一次最多几条 | 3 | 分段的上限 |
| 表情包目录 | 空 | 留空 = 程序目录下的 `memes/` |

### 免 @ 接话
| 项 | 默认 | 说明 |
|---|---|---|
| @ 激活保活 | 开 | @ 一次之后一段时间内不用再 @ |
| 保活时长（秒） | 60 | 静默满这么久窗口关闭 |
| 合并连发消息 | 开 | 连着的几条合成一条再回 |
| 静默多久算说完（秒） | 3 | 每来一条会重新计时 |
| 最长等多久（秒） | 15 | 从第一条算起的硬上限 |

### 语音回复
| 项 | 默认 | 说明 |
|---|---|---|
| 语音回复 | 关 | 总开关（还要在人设里给角色勾上） |
| 语音最长字数 | 20 | 超过改发文字 |
| 语音合成模型 | `mimo-v2.5-tts-voicedesign` | 共用上面的 Base URL 和 Key |

### 消息格式
| 项 | 默认 | 说明 |
|---|---|---|
| 消息带上昵称与时间 | 开 | 群聊里分得清谁在说话 |
| 群聊引用原消息 | 关 | 回复时引用原消息，群里会显得略吵 |
| 引用消息 | 开 | 让机器人看到被引用的内容 |

### 安全与通知
| 项 | 默认 | 说明 |
|---|---|---|
| 私聊出错时告知原因 | 开 | 关闭后只写日志 |
| 屏蔽词 | 空 | 命中直接忽略该消息 |

## 常见问题

### 首次登录可能出现的"两次扫码"

NapCat 首次登录会先写一份账号配置，QLark 检测到之后会重启一次 NapCat 让它生效，
所以**可能要扫两次码**。这是正常的，扫完就会进入"已登录"。

### 卡在"已登录，正在初始化…" / 消息发不出去

多数是 OneBot 端口没通。检查：

1. NapCat 是否真的在跑（任务管理器里能看到）
2. 「模型配置 → NapCat 连接」里的端口和 NapCat 配置是否一致
3. 日志页有没有 `连接失败` / `HTTP 401`

### 机器人"在线但完全不回复"

按顺序排查：

1. **群里没 @ 它** —— 群聊默认必须 @（或者用了免 @ 保活）
2. **暂停了** —— 仪表盘上有没有「已暂停」标签
3. **限流** —— 同一会话一分钟内回太多次会被拦，日志里有提示
4. **敏感词** —— 命中的消息会被直接忽略
5. **模型报错** —— 看日志里有没有 `HTTP 4xx` / `余额不足`

### 语音发不出去

先看日志里有没有这几行：

```
语音合成完成（mp3，18.5 KB，语气「开心」）
语音文件X需要转换成silk
转换成功! 时长: 2.616
发送 -> 私聊 (…) [语音 2s]
```

- 只有第一行没有后面的 → NapCat 的 ffmpeg 组件有问题，重装 NapCat 运行时
- 一行都没有 → 模型没选语音，或者语音总开关 / 人设开关没开

### 引用内容取不到

日志里会有 `引用消息取不到内容（id=…）`。可能是原消息被撤回了，
或者 NapCat 版本对 `get_msg` 的返回结构不同。这条不影响回复，只是看不到引用内容。

## 开发

### 测试

```powershell
$env:PYTHONIOENCODING='utf-8'
.\.venv\Scripts\python.exe -m pytest -q
```

测试完全跑在假的 NapCat 和假的 OpenAI 服务上，不需要真的 QQ 号，也不会发真消息。

### 打包成 exe

```powershell
python tools\build_exe.py --clean-dir C:\some\empty\dir
```

> **不要直接运行你要分发的那份。** 它会往自己目录写 QQ 配置和登录态，
> 所以用 `--clean-dir` 指定一个干净的输出目录。

### 「像不像人」评测

改提示词不能靠"我觉得好点了"：

```powershell
python tools\eval_humanity.py              # 18 个场景各跑 1 次
python tools\eval_humanity.py --runs 3     # 每场景 3 次，减少偶然性
python tools\eval_humanity.py --no-rubric  # 关掉判断表做对照
```

评分是**启发式**的（数关键词、判断有没有追问词），不是让模型自评 ——
那样既贵又不可复现。分数只用来比较「改前 vs 改后」，不追求绝对正确。

## 数据与配置

所有用户数据都在 **`%LOCALAPPDATA%\QLark`**：

| 路径 | 内容 |
|---|---|
| `data\qlark.db` | 配置、人设、记忆、统计（SQLite） |

## 已知限制

- **只支持 Windows**（依赖 Edge WebView2 与 NapCat 的 Windows 运行时）
- 仅适配 OneBot 11 的 HTTP 通信方式，不支持的实现需要改 `onebot/`
- 语音合成目前按 MiMo 的 `voicedesign` 接口实现，换服务要改 `llm/tts.py`
- 群里所有人共用一份记忆，人多了会串味 —— 这是设计取舍，不是 bug
